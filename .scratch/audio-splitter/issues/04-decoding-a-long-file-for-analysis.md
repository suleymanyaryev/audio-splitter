# Decoding a long file for analysis

Type: research
Status: resolved

## Question

Detection needs the source file as raw samples (PCM), but 2 h of stereo 32-bit float at 44.1 kHz is about 2.5 GB. Which ways of getting from a 1–3 h `.mp3`, `.m4a` or `.opus` file to analysis samples are workable in desktop Chrome, and what does each cost?

Compare, with sources:

- **ffmpeg.wasm decoding to raw PCM** (`-f f32le` or `s16le`): expected speed relative to real time for each codec on the single-thread core, whether decoding can be done in time slices (`-ss`/`-t`) so memory stays bounded, and whether output can be read incrementally.
- **ffmpeg.wasm with `-ac 1 -ar <low rate>`**: the same, with ffmpeg doing the downmix and downsample. Note what its resampler does (low-pass filter before decimation) so a hand-written version can be compared against it.
- **WebCodecs `AudioDecoder`**: codec support in Chrome for MP3, AAC and Opus, and what would have to supply the demuxed packets when ffmpeg.wasm is the only container library.
- **`decodeAudioData` / `OfflineAudioContext`**: whether it can decode at a reduced sample rate or in slices, and where it fails on long files.

For each option give: memory high-water mark for a 2 h file, rough time, and which learnable steps (decoding in chunks, downmixing, downsampling) stay visible in hand-written code versus disappear into a flag.

Also answer: what analysis sample rate is enough for RMS-based gap detection, and why.

Answer with a ranked recommendation and the measurements the spike must take.

## Answer

Researched on 2026-11-13. Every statement below is marked as one of three kinds: **[source]** means a specification, documentation page or source file states it; **[measured]** means it was measured here with native ffmpeg 8.1 on the real sample `samples/sample1.m4a` (AAC-LC, 44.1 kHz stereo, 61 min 26 s, 89 MB), read-only and through pipes with no audio file written; **[inferred]** means it is reasoning from the first two and has not been confirmed. Nothing was run in ffmpeg.wasm or in Chrome: every wasm and browser number is an estimate for the spike to replace. No MP3 or Opus file was available, so those two codecs are covered from sources only.

### Terms used

- **PCM** (pulse-code modulation) is audio stored as a plain list of numbers, one number per channel per instant, with no compression. "Raw samples" and PCM mean the same thing here. `f32le` is PCM where each number is a 32-bit float between −1 and 1; `s16le` is PCM where each number is a 16-bit integer between −32768 and 32767.
- **Sample rate** is how many of those numbers per second describe one channel: 44 100 per second (44.1 kHz) for most music files, always 48 000 for Opus as ffmpeg decodes it.
- A **frame** is one instant of sound: one sample for each channel. Stereo has two samples per frame.
- **Decoding** turns the compressed codec data (MP3, AAC, Opus) back into PCM.
- **Demuxing** is the step before decoding: opening the container (`.mp3`, `.m4a`, `.opus`) and cutting it into the individual compressed packets that a decoder accepts one at a time.
- **Downmix** means turning several channels into fewer, here stereo into mono, by adding left and right with some weight.
- **Resampling** means changing the sample rate. **Downsampling** is resampling to a lower rate, and **decimation** is its simplest form: keep one sample out of every N.
- **Aliasing** is the error that decimation causes when nothing is filtered first. A sample rate can only describe frequencies up to half of itself (the Nyquist limit); any sound above that limit does not disappear when samples are dropped, it shows up as a false lower frequency. A **low-pass filter** removes the high frequencies before decimation so there is nothing left to alias.

### Ranked recommendation

1. **First choice: ffmpeg.wasm decodes the source file in time slices to full-rate stereo `f32le`, and everything after decoding is hand-written.** One `exec` per slice (`-ss <start> -t <length> -i <source> -vn -f f32le slice.pcm`, a slice of about 5 minutes), then the app reads the slice, downmixes it, updates the loudness curve and the waveform peaks, deletes the slice file and moves on. The reason is that this is the only option that satisfies both constraints at once: ffmpeg.wasm stays the only container library, and all three learnable steps (the slice loop, the downmix, the downsample) are ordinary TypeScript the owner can read. Memory is set by the slice length and not by the length of the source file: about 0.25 GB for 5-minute slices [inferred from the arithmetic below]. The loop also gives honest progress ("slice 7 of 24") and a natural place to cancel.
2. **Fallback: one ffmpeg.wasm `exec` over the whole source file with `-ac 1 -ar 8000 -f f32le`.** This produces 230 MB for 2 h in a single run and needs no slicing. It is the fallback, not the first choice, because the downmix and the downsample disappear into two flags and there is no slice loop left to read. It becomes the right choice if the spike shows that per-slice `exec` calls are slow, leak memory, or give wrong slice boundaries for MP3 or Opus. The hand-written downmix and downsample can then still exist as tested functions that are compared against this output on one slice, but they are no longer on the path that produces the result.
3. **Escape hatch only: WebCodecs `AudioDecoder`.** It is expected to be the fastest and keeps all three steps hand-written, but Chrome's decoder needs demuxed packets and ffmpeg.wasm cannot hand packets to JavaScript one at a time. That means three hand-written container parsers (or a second container library), which is exactly the container work the owner assigned to ffmpeg.wasm. Consider it only if the spike shows ffmpeg.wasm decoding takes minutes.
4. **Not recommended: `decodeAudioData`.** Chrome decodes the whole file at full rate into memory before anything else happens, which is 5 GB or more for a 2 h file, and it cannot decode in slices.

### Memory arithmetic for a 2 h source file

The rule is bytes = seconds × sample rate × channels × bytes per sample, and 2 h is 7 200 s.

| What | Calculation | Size |
| --- | --- | --- |
| Stereo `f32le` at 44.1 kHz (MP3, AAC) | 7 200 × 44 100 × 2 × 4 | 2 540 160 000 B ≈ 2.54 GB |
| Stereo `f32le` at 48 kHz (Opus) | 7 200 × 48 000 × 2 × 4 | 2 764 800 000 B ≈ 2.76 GB |
| Stereo `s16le` at 44.1 kHz | 7 200 × 44 100 × 2 × 2 | 1 270 080 000 B ≈ 1.27 GB |
| Mono `f32le` at 8 kHz | 7 200 × 8 000 × 1 × 4 | 230 400 000 B ≈ 230 MB |
| Mono `s16le` at 8 kHz | 7 200 × 8 000 × 1 × 2 | 115 200 000 B ≈ 115 MB |
| One 5-minute slice, stereo `f32le` at 44.1 kHz | 300 × 44 100 × 2 × 4 | 105 840 000 B ≈ 106 MB |
| One 1-minute slice, stereo `f32le` at 44.1 kHz | 60 × 44 100 × 2 × 4 | 21 168 000 B ≈ 21 MB |
| Loudness curve, one float per 50 ms window | 7 200 ÷ 0.05 × 4 | 576 000 B ≈ 0.6 MB |

Two facts about ffmpeg.wasm turn an output size into a high-water mark. First, an output file lives in Emscripten's in-memory file system (MEMFS) as one JavaScript `Uint8Array` that grows by 12.5 % at a time, copying the old contents into the new array each time, so while it grows the worker briefly holds the old and the new array together [source: `library_memfs.js`, `expandFileStorage`]. Second, `readFile` allocates a second array of the full file size and copies the file into it before transferring it to the page [source: `library_fs.js`, `readFile`; `worker.ts`]. A file of size S therefore costs up to about 2.1 × S, both while it is written and while it is read back [inferred]. The source file itself costs nothing extra if it is mounted with WORKERFS, which reads byte ranges from the `File` on demand [source: `library_workerfs.js`]; if it is copied in with `writeFile` instead, add the file size (100–700 MB).

### What sample rate is enough for the loudness curve, and why

**Short answer: about 8 kHz mono is enough with a very wide margin, and in the recommended design no downsampling is needed at all for the loudness curve.**

The reasoning from first principles has four parts.

1. **What the loudness curve needs.** RMS (root mean square) is the square root of the average of the squared samples in a window. It answers one question per 50 ms window: how much energy is here? A gap is a run of windows whose answer stays under the silence threshold. Nothing in that needs to know *which* frequencies are present, only roughly how much sound there is.
2. **What a lower sample rate takes away.** Lowering the sample rate has two effects. It lowers the highest frequency that can be represented (half the sample rate: 4 kHz at an 8 kHz rate), and it leaves fewer samples in each window (2 205 per 50 ms window at 44.1 kHz, 400 at 8 kHz, 50 at 1 kHz). The first effect matters little because the energy of music sits overwhelmingly in the bass and the middle, below 4 kHz. The second matters little as long as a few hundred samples remain, because an average over a few hundred values is already steady. The time resolution of the curve is set by the window length (50 ms), not by the sample rate.
3. **What was measured on the real sample.** The loudness curve was computed at 44.1 kHz from a hand-written downmix and compared, window by window, with curves computed at lower rates [measured, native ffmpeg, AAC sample, 73 724 windows]:

   | Analysis rate | How it was made | Difference from the 44.1 kHz curve (mean / 99th percentile) | Gaps found at −45, −40, −30 dB (minimum gap length 1 s) |
   | --- | --- | --- | --- |
   | 16 kHz | ffmpeg `-ar` | 0.00 dB / 0.01 dB | identical (20, 37, 61) |
   | 8 kHz | ffmpeg `-ar` | 0.01 dB / 0.03 dB | identical |
   | 8.82 kHz | hand-written, every 5th sample, no filter | 0.00 dB / 0.02 dB | identical |
   | 4 kHz | ffmpeg `-ar` | 0.01 dB / 0.07 dB | same gaps, splits moved by at most 25 ms |
   | 2 kHz | ffmpeg `-ar` | 0.04 dB / 0.30 dB | same count, splits moved by up to 150 ms |
   | 1 kHz | ffmpeg `-ar` | 0.40 dB / 4.36 dB | different gap lists |

   At a fourth threshold, −35 dB, every rate at or below 8.82 kHz found 45 gaps where the full rate and 16 kHz found 44: one stretch sits within a few hundredths of a decibel of the threshold, so any tiny change tips it. That is a property of thresholds, not of the sample rate.
4. **Why the sample rate is not the thing to worry about.** In this sample the gaps are not digital silence. With ffmpeg's `silencedetect` and a 1 s minimum, −50 dB finds no gap, −40 dB finds 7 and −30 dB finds about 33, while the mean level of the music is −14.8 dB [measured by the coordinator]. The gaps therefore sit roughly 25 to 35 dB under the mean level of the music, and moving the silence threshold by 10 dB changes the result by tens of gaps. The error introduced by analysing at 8 kHz is under 0.1 dB. The silence threshold matters far more than the sample rate. (The loudness-curve detector above finds more gaps at −40 dB than `silencedetect` does, 37 against 7, because `silencedetect` tests every single sample against the threshold while a 50 ms RMS window averages; the two counts are not comparable and the spike should calibrate the threshold on the loudness curve itself.)

**A point worth teaching: aliasing does not hurt RMS.** Keeping every 5th sample with no filter aliases badly and would sound wrong, yet its loudness curve matched the full-rate curve with an offset of 0.00 dB at every rate tried [measured]. The reason is that aliasing moves energy to the wrong frequency but does not remove it, and RMS only counts energy. A proper low-pass filter does the opposite: it removes the energy above the new limit, which is the right thing for listening and makes almost no difference for music's loudness. So for this app a hand-written decimator is *sufficient*, and a hand-written low-pass filter is a lesson rather than a requirement.

**Practical consequence.** In option 1 the slice is already in memory at full rate, so the loudness curve and the waveform peaks can be computed straight from it and only the small results are kept (0.6 MB of loudness curve for 2 h). Downsampling is then a learning milestone and a way to keep a compact copy of the samples, not something detection depends on. If a downsampled copy is kept, use an integer factor so the hand-written code stays simple: every 5th sample from 44.1 kHz gives 8 820 Hz, every 6th from 48 kHz gives 8 000 Hz. Do not go below about 4 kHz.

### Findings

#### ffmpeg.wasm decoding to raw PCM

- **The core is ffmpeg n5.1.4 built without hand-written assembly.** The build uses Emscripten 3.1.40, `FFMPEG_VERSION=n5.1.4` and `--disable-asm`; the single-thread core starts at 32 MB of wasm memory with growth allowed and sets no maximum, so Emscripten's default ceiling of 2 GB applies [source: [Dockerfile](https://github.com/ffmpegwasm/ffmpeg.wasm/blob/main/Dockerfile), [build/ffmpeg.sh](https://github.com/ffmpegwasm/ffmpeg.wasm/blob/main/build/ffmpeg.sh), [build/ffmpeg-wasm.sh](https://github.com/ffmpegwasm/ffmpeg.wasm/blob/main/build/ffmpeg-wasm.sh), [Emscripten settings.js](https://github.com/emscripten-core/emscripten/blob/3.1.40/src/settings.js)]. This is the state of the `main` branch on the day of research; which core version the project installs is ticket 02's question.
- **Native speed, for an order of magnitude.** Decoding the 61-minute AAC sample to the null output with one decoder thread took 2.97–3.02 s, about 1 230 times faster than real time, which scales to about 6 s for 2 h. Adding `-ac 1 -ar 8000` took 3.01–3.29 s. Running with `-cpuflags 0` (ffmpeg's switch for turning off processor-specific code) made no clear difference (3.02–3.80 s) [measured: native ffmpeg 8.1, an x86_64 build running under Rosetta 2 on an Apple M4 Pro; AAC only; three runs each]. This is a native number and says nothing directly about wasm.
- **Published wasm slowdown figures.** A study of the SPEC CPU benchmarks found WebAssembly slower than native code by 45 % (Firefox) to 55 % (Chrome) on average, with a worst case of 2.5 times in Chrome [source: [Jangda et al., USENIX ATC 2019](https://www.usenix.org/conference/atc19/presentation/jangda)]. The ffmpeg.wasm project's own benchmark is far worse: 128.8 s against 5.2 s native, a factor of 25, for the single-thread core transcoding a WebM video to MP4 on an 8-thread Intel i5 in Chrome 116 [source: [ffmpeg.wasm performance page](https://ffmpegwasm.netlify.app/docs/performance)]. That test is video encoding against a multi-threaded native ffmpeg with assembly, so it is a pessimistic bound for single-thread audio decoding.
- **Estimated wasm time.** Applying 1.5 to 2.5 times to the native 6 s gives 9–15 s for 2 h of AAC; applying 25 times gives about 2.5 min [inferred]. No published measurement of ffmpeg.wasm audio decoding speed per codec was found, and nothing was measured for MP3 or Opus, so the per-codec speed on the single-thread core is unknown until the spike measures it.
- **Decoding in time slices works and keeps memory bounded.** `-ss` before `-i` seeks in the input; ffmpeg seeks to the closest point before the position and, because `-accurate_seek` is on by default when decoding, decodes and discards the audio between that point and the requested position. `-t` before `-i` limits how much is read [source: [ffmpeg documentation](https://ffmpeg.org/ffmpeg.html)]. On the AAC sample, 13 slices of 300 s produced exactly the same number of frames as one whole decode (162 562 048), with nothing lost or repeated at the slice borders [measured, native 8.1].
- **Slices are not bit-identical to a whole decode, and that does not matter here.** About 1.2 % of the samples differed between the sliced and the whole decode, spread throughout the slices. The loudness curves of the two differed by 0.0001 dB on average, 1.90 dB at worst, and by more than 0.5 dB in 3 of 73 724 windows [measured]. The likely cause is that ffmpeg's AAC decoder fills some frequency bands with generated noise from a random-number generator that is seeded once when the decoder starts and then runs on, so a decoder started in the middle of the file produces different (equally valid) noise [source for the mechanism: [aacdec_template.c](https://github.com/FFmpeg/FFmpeg/blob/n5.1.4/libavcodec/aacdec_template.c); inferred as the cause]. Do not write a test that expects sliced and whole decodes to be equal sample for sample.
- **Slicing costs little natively.** Piping `f32le` out took 4.70 s whole, 5.15 s as 13 slices of 300 s and 7.06 s as 62 slices of 60 s, about 0.04 s extra per slice; a 60 s slice at the end of the file took the same time as one at the start (0.110 s against 0.103 s), so seeking in `.m4a` is free [measured, native]. The start-up cost of one `exec` in wasm is unknown.
- **MP3 seeking is accurate by default but gets slower towards the end of the file.** In n5.1.4 the MP3 demuxer's own seek is only used when `usetoc` or the fast-seek flag is set; `usetoc` defaults to off, and otherwise the function returns −1 with the comment "generic index code", meaning ffmpeg reads forward through the file's frames to find the position [source: [mp3dec.c](https://github.com/FFmpeg/FFmpeg/blob/n5.1.4/libavformat/mp3dec.c)]. Each slice therefore re-reads the file from the start up to its own position, so the total reading grows with the square of the slice count; with 24 slices of a 170 MB file that is roughly 2 GB of reads through WORKERFS [inferred]. Whether that is seconds or a minute in Chrome is for the spike.
- **Opus needs a short run-in after a seek.** A player seeking in Ogg Opus should start decoding at least 3 840 samples (80 ms) before the target and discard them so the output is correct at the target, and Ogg Opus positions are always counted at 48 kHz [source: [RFC 7845](https://www.rfc-editor.org/rfc/rfc7845.html), sections 4 and 4.6]. Whether ffmpeg n5.1.4 in wasm produces gap-free slice borders for Opus was not measured.
- **Output cannot be read while `exec` is running.** The worker handles an `exec` message by calling ffmpeg synchronously, so it cannot answer a `readFile` message until ffmpeg returns [source: [worker.ts](https://github.com/ffmpegwasm/ffmpeg.wasm/blob/main/packages/ffmpeg/src/worker.ts)]. Users report the same: "I could not access the ffmpeg filesystem at all while an ffmpeg.exec() command is running" [source: [discussion 486](https://github.com/ffmpegwasm/ffmpeg.wasm/discussions/486)]. Standard output is not a way round it, because the core forwards it as text log lines [source: [bind.js](https://github.com/ffmpegwasm/ffmpeg.wasm/blob/main/src/bind/ffmpeg/bind.js)]. Reading incrementally therefore means one `exec` per slice, which is option 1.
- **Raw PCM carries no description of itself.** The raw PCM muxers "do not store timestamps or metadata" [source: [ffmpeg formats documentation](https://ffmpeg.org/ffmpeg-formats.html)], so the app must already know the sample rate and channel count of what it reads (from the log of the first `exec`, or from `ffprobe`, which the `FFmpeg` class exposes [source: [ffmpeg.wasm API](https://ffmpegwasm.netlify.app/docs/api/ffmpeg/classes/FFmpeg/)]).
- **Repeated `exec` calls have an open bug report.** An open issue describes intermittent "memory access out of bounds" errors on some inputs, reproduced by a second user in 2 to 5 of 20 runs, with no maintainer reply [source: [issue 823](https://github.com/ffmpegwasm/ffmpeg.wasm/issues/823)]. It concerns video frames, not audio, but option 1 makes 24 or more `exec` calls on one instance, so the spike must check for failures and memory growth.
- **The progress event is not usable for slices.** The documentation says progress is "accurate only when the length of input and output video/audio file are the same" [source: ffmpeg.wasm API, as above]. With slices the app counts slices itself.

#### ffmpeg.wasm with `-ac 1 -ar <low rate>`, and what the resampler does

- **`-ac` sets the number of channels and `-ar` the sample rate** [source: ffmpeg documentation]. Both are carried out by ffmpeg's libswresample ("swr"), which is the default resampler [source: [ffmpeg resampler documentation](https://ffmpeg.org/ffmpeg-resampler.html)].
- **How swr downsamples.** It is a low-pass filter followed by decimation, done in one step. The filter is a windowed sinc: the ideal low-pass shape (sinc) cut to a finite length with a Kaiser window (`filter_type` defaults to kaiser, `kaiser_beta` 9). The cut-off defaults to 0.97 of the new Nyquist limit, the filter is 32 samples long at the *output* rate (`filter_size` 32), and it is stored for up to 1 024 fractional positions (`phase_shift` 10), or for an exact count worked out from the two rates when `exact_rational` can find one (it is on by default), with linear interpolation between positions [source: resampler documentation; [options.c](https://github.com/FFmpeg/FFmpeg/blob/n5.1.4/libswresample/options.c); [resample.c](https://github.com/FFmpeg/FFmpeg/blob/n5.1.4/libswresample/resample.c)]. For 44.1 kHz to 8 kHz that means a cut-off at 0.97 × 4 000 = 3 880 Hz and a filter of ceil(32 ÷ (8 000 × 0.97 ÷ 44 100)) = 182 input samples for each output sample [inferred from `resample.c`].
- **How swr downmixes stereo to mono, and the 3 dB surprise.** The mixing weights for left and right are each 1/√2 ≈ 0.707. They are scaled down so they sum to 1 (0.5 each) only when the output or internal sample format is an integer format; for float in and float out they are left at 0.707 [source: [rematrix.c](https://github.com/FFmpeg/FFmpeg/blob/n5.1.4/libswresample/rematrix.c)]. So `-ac 1 -f f32le` gives 0.707 × (L + R), which is 3.01 dB louder than the usual hand-written (L + R) ÷ 2. This was confirmed on the sample: the loudness curve from `-ac 1` sat exactly 3.01 dB above the one from a hand-written average in every window [measured, native 8.1]. A hand-written downmix compared against ffmpeg's will be off by this constant, and a silence threshold tuned on one will be 3 dB wrong on the other. The `s16le` case (expected weights 0.5) was read from the source and not measured.
- **Cost.** Natively the resample added about 10 % or less to the decode time [measured]. The 2 h output is 230 MB as `f32le` or 115 MB as `s16le`, small enough to produce in one `exec` without slicing.

#### WebCodecs `AudioDecoder`

- **The three codecs are registered, but support is the browser's choice.** The registry lists `mp3`, `mp4a.*` (AAC) and `opus`, and states that implementers "are not required to support any particular codec nor registry entry" [source: [WebCodecs codec registry](https://w3c.github.io/webcodecs/codec_registry.html)]. `AudioDecoder.isConfigSupported()` returns a promise with a `supported` flag for a given configuration [source: [WebCodecs](https://w3c.github.io/webcodecs/)].
- **Chrome's source says all three decode.** Chromium's supported-types function returns true for MP3 and Opus unconditionally, and routes AAC through a separate check; AAC is classed as a proprietary codec, which means it is present in Google Chrome but absent from Chromium builds made without proprietary codecs [source: [media/base/supported_types.cc](https://github.com/chromium/chromium/blob/main/media/base/supported_types.cc)]. The shared web-platform tests exercise `mp3`, `opus`, AAC in MP4 and AAC in ADTS, with `mp4a.40.2` as the AAC codec string [source: [audioDecoder-codec-specific test](https://github.com/web-platform-tests/wpt/blob/master/webcodecs/audioDecoder-codec-specific.https.any.js)]. This was read from source, not run: the spike should call `isConfigSupported` once. A compatibility table found through search gives Chrome 94 as the first version with `AudioDecoder`; this was not confirmed on a primary page. `AudioDecoder` is available in dedicated workers [source: [MDN AudioDecoder](https://developer.mozilla.org/en-US/docs/Web/API/AudioDecoder)].
- **What a packet must be for each codec.** MP3: one MP3 frame, no `description` [source: [MP3 registration](https://www.w3.org/TR/webcodecs-mp3-codec-registration/)]. AAC: with no `description` the data is assumed to be ADTS frames; with a `description` (an AudioSpecificConfig) it is assumed to be raw AAC frames as stored in `.m4a` [source: [AAC registration](https://www.w3.org/TR/webcodecs-aac-codec-registration/)]. Opus: with no `description` each chunk is one Opus packet [source: [Opus registration](https://www.w3.org/TR/webcodecs-opus-codec-registration/)]; Chrome requires a `description` only for Opus with more than two channels [source: [webcodecs/audio_decoder.cc](https://github.com/chromium/chromium/blob/main/third_party/blink/renderer/modules/webcodecs/audio_decoder.cc)].
- **What would supply the packets.** ffmpeg.wasm runs whole commands and returns files, so it cannot feed packets to JavaScript one by one. The realistic routes are [inferred]: for MP3, a hand-written parser that reads each frame header to find the frame length (an MP3 file is a plain sequence of frames, after an optional ID3 tag); for AAC, an ffmpeg.wasm stream copy to `-f adts` ("Audio Data Transport Stream muxer. It accepts a single AAC stream" [source: ffmpeg formats documentation]) followed by a hand-written parser of the 7-byte ADTS headers; for Opus, a hand-written Ogg page parser that reassembles packets from the page's segment table. That is three small demuxers in the app.
- **Output and memory.** The decoder returns `AudioData` blocks at the stream's own sample rate; there is no resampling option. `copyTo` can always convert to planar 32-bit float ("Conversion from any AudioSampleFormat to f32-planar MUST always be supported"), `decodeQueueSize` and the `dequeue` event let the app avoid feeding packets faster than they are decoded, and each `AudioData` must be closed to release its memory [source: WebCodecs; [MDN AudioData](https://developer.mozilla.org/en-US/docs/Web/API/AudioData)]. Memory is therefore a few packets and blocks at a time.

#### `decodeAudioData` and `OfflineAudioContext`

- **Reduced sample rate: yes on paper, no in memory.** The result is resampled "to the sample-rate of the BaseAudioContext if it is different from the sample-rate of audioData", and an `OfflineAudioContext` can be created at any rate from 3 000 to 768 000 Hz [source: [Web Audio API](https://webaudio.github.io/web-audio-api/), sections 1.1 and 2.4; [MDN OfflineAudioContext](https://developer.mozilla.org/en-US/docs/Web/API/OfflineAudioContext/OfflineAudioContext)]. So a context at 8 000 Hz returns an 8 kHz buffer. But Chrome first decodes the entire file at its own rate and only then resamples: `CreateBusFromInMemoryAudioFile` calls `DecodeAudioFileData` and afterwards `TryCreateBySampleRateConverting`, with the mix-to-mono argument false, so the channels are kept [source: [audio_bus.cc](https://github.com/chromium/chromium/blob/main/third_party/blink/renderer/platform/audio/audio_bus.cc), [base_audio_context.cc](https://github.com/chromium/chromium/blob/main/third_party/blink/renderer/modules/webaudio/base_audio_context.cc)].
- **Where the memory goes.** The decoder collects every decoded packet in a list, then allocates one buffer for the whole file and copies the packets into it, so two full-rate float copies exist together: 2 × 2.54 GB ≈ 5.1 GB for 2 h at 44.1 kHz stereo, on top of the compressed file, which must be passed in as one `ArrayBuffer` [source for the mechanism: [content/renderer/media/audio_decoder.cc](https://github.com/chromium/chromium/blob/main/content/renderer/media/audio_decoder.cc), [audio_file_reader.cc](https://github.com/chromium/chromium/blob/main/media/filters/audio_file_reader.cc); total inferred, not measured].
- **Slices: no.** "This method only works on complete file data, not fragments of audio file data" [source: [MDN decodeAudioData](https://developer.mozilla.org/en-US/docs/Web/API/BaseAudioContext/decodeAudioData)].
- **It is not designed for long files.** The specification says of `AudioBuffer`: "it would be expected that the length of the PCM data would be fairly short (usually somewhat less than a minute). For longer sounds, such as music soundtracks, streaming should be used" [source: Web Audio API]. A Chromium media engineer wrote of a one-hour MP3 that "decodeAudioData will decode everything in memory which is a bit excessive" [source: [chromium-dev thread, April 2021](https://groups.google.com/a/chromium.org/g/chromium-dev/c/sXkjxXDeqz8)].
- **Not confirmed.** No Chromium issue with a measured failure size was found, and the exact behaviour at the limit (a rejected promise or a crashed tab) was not tested. The allocation calls in the source are the kind that return "failed" instead of aborting, which suggests a rejected promise [inferred].

### For the spike to verify

All of these are measured in desktop Chrome with the single-thread core, first on `samples/sample1.m4a` and then on an MP3 and an Opus file once real ones exist.

1. **Decode speed per codec.** Wall-clock time of the `exec` calls for a full-rate stereo `f32le` decode, expressed as "times faster than real time", for AAC, MP3 and Opus. This replaces the 10 s to 2.5 min estimate.
2. **Slice length.** Total time and peak memory with 60 s, 300 s and 600 s slices, to find the cost of one `exec` start-up and choose a length.
3. **Peak memory.** The tab's memory while a 300 s slice is written and read back (expected about 0.25 GB), and that it returns to the baseline after `deleteFile`.
4. **Stability over many runs.** 25 to 125 consecutive `exec` calls on one instance without a "memory access out of bounds" error and without memory creeping upward.
5. **Slice borders per codec.** The frames of all slices add up to the frames of one whole-file run (for a file short enough to decode whole), for AAC, MP3 and Opus on ffmpeg n5.1.4, and the loudness curve shows no dip or spike at a slice border.
6. **MP3 seek cost.** Time of the last slice against the first slice of a long MP3 mounted with WORKERFS; if the last is much slower, try longer slices before trying `-fflags +fastseek`, which trades accuracy for speed.
7. **WORKERFS with `-ss`.** That input seeking works on a mounted `File` and that the source file is not copied into memory.
8. **Reading a slice.** That the `Uint8Array` from `readFile` can be viewed as a `Float32Array` without copying, and that its length is a whole number of stereo frames.
9. **Hand-written analysis time.** Time to downmix a slice and update the loudness curve and peaks, summed over the file (expected a few seconds for 2.54 GB of samples).
10. **The fallback.** Time and peak memory of one `exec` with `-ac 1 -ar 8000 -f f32le` over the whole file (expected output 230 MB for 2 h, about 0.5 GB peak).
11. **Downmix comparison.** That a hand-written (L + R) ÷ 2 differs from ffmpeg's `-ac 1 -f f32le` by a constant 3.01 dB in the wasm core as well, and what `-ac 1 -f s16le` gives.
12. **Downsample comparison.** The loudness curve from a hand-written "every 5th sample" decimation against the one from `-ar 8000` and against full rate, to confirm in the browser that the three agree to within about 0.1 dB.
13. **Threshold calibration.** Which silence threshold on the 50 ms loudness curve recovers the real track borders of the sample, given that −40 dB already yields 37 gaps there against 7 from `silencedetect`.
14. **Escape hatch.** One call of `AudioDecoder.isConfigSupported` each for `mp3`, `mp4a.40.2` and `opus` in the target Chrome, so the answer is on record if option 3 is ever needed.
